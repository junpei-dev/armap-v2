## 1. 設計の基本方針

| 方針 | 理由 |
|---|---|
| **データとプログラムを分ける** | 部屋や経路の追加を、管理コンソールでのデータ入力だけで済ませる。生徒はプログラムを書かずにデータを整備できる |
| **距離・方向はデータに持たず、座標から計算する** | 「距離は12m」「方向は右」を手で書くと、座標と食い違ったときにどちらが正しいか分からなくなる |
| **経路計算・向きの計算・データ検査はReactから切り離す** | 純粋なTypeScriptの関数にしてテストできるようにする。データ検査は、ブラウザ（管理コンソール）とサーバー（保存時）の両方で同じ関数を使う |
| **地図は図面の画像を使わず、データから描く** | 図面を公開しない。拡大しても線がぼけない |
| **案内の主役はセンサー不要の表示** | 全体マップと文字の案内はどの端末でも必ず動く。AR表示は付加機能とし、壊れても案内は続けられる |
| **保存は即反映、ただし壊れたデータは保存させない** | 生徒の入力を待たずに来校者の画面に反映する。その代わり、保存時に検査し、変更履歴から戻せるようにする |


| 利用者 | 入口 | 認証 |
|---|---|---|
| 来校者 | `https://armap-v2.pages.dev/?cp=CP01` | なし |
| 生徒・教員（データ入力） | `https://armap-v2.pages.dev/admin` | 学校のメールアドレス＋個人ごとのパスコード（5.7） |
| 教員（プログラム・設定） | 教師用PC → GitHub / Cloudflare ダッシュボード | GitHub・Cloudflare のアカウント |

- カメラ映像・センサーの値は端末の中だけで使い、どこにも送らない

## 4. 座標系

### 4.1 全体座標系

校地全体で共通の座標系を1つだけ使う。

| 項目 | 定義 |
|---|---|
| 基準 | 配置図（図面1ページ目）を**画面に表示したときの向き**（ページの上が上） |
| 単位 | メートル |
| x軸 | 右向きが正 |
| y軸 | **下向きが正**（SVGの座標と同じ。地図をそのまま描ける） |
| 原点 | 配置図ページの左上隅（後から平行移動しても計算には影響しない） |
| 階 | 整数（1, 2, 3, 4）。座標とは別に持つ |

### 4.2 角度の決め方

| 項目 | 定義 |
|---|---|
| 図面角度 | 図面の**上を0度、時計回りに正**（右＝90度、下＝180度、左＝270度） |
| 方位との関係 | 方位（北0度・時計回り）＝図面角度＋`mapNorthBearing`。`mapNorthBearing` は「図面の上方向が北から何度か」 |
| `mapNorthBearing` の初期値 | **未設定（null）**。要件どおり図面を正とし、磁気コンパスを補助に使うと決めた時点で現地で実測して設定する |

図面角度を方位と同じ「上0度・時計回り」にしておくと、実測値を足すだけで方位に変換できる。

2点間の図面角度は次で求める（y軸が下向きなので符号に注意）。

```ts
// a から b へ向かう図面角度（0〜360度）
function planAngle(a: Point, b: Point): number {
  const deg = (Math.atan2(b.x - a.x, -(b.y - a.y)) * 180) / Math.PI;
  return (deg + 360) % 360;
}
```

### 4.3 PDFから全体座標への変換

調べた結果、施設台帳PDFは**全ページが線（ベクター）データ**で、ページが270度回転した状態で保存されている。PyMuPDF で線を読み、次の手順で全体座標に変換する。

1. `page.get_drawings()` で線分を取り出す（PDF内部の座標・単位はpt）
2. `page.rotation_matrix` を掛けて、画面に表示したときの座標に直す
3. 縮尺1/1600なので `1pt = 25.4 / 72 × 1600 / 1000 = 0.56444 m` を掛ける

**精度の確認**: 配置図から抜き出した長方形の寸法と、平面図（1/600）に書かれた寸法を比べた。

| 棟 | 配置図から抽出 | 平面図の寸法 |
|---|---|---|
| ㉘ 機械科実習棟 | 40.0 × 10.0 m | 40.00 × 10.00 m |
| ㊸ 普通教室棟 | 44.0 × 9.3 m | 44.00 × 9.30 m |
| 64 機械科実習棟 | 39.3 × 13.0 m | 39.30 × 13.00 m |
| 66 生活文化科棟 | 31.9 × 13.0 m | 31.90 × 13.00 m |

→ 配置図の線データは**0.1m単位で平面図と一致**する。手で測る必要はなく、棟の位置と外形は抽出スクリプトで取り出せる。

### 4.4 棟の中の座標（平面図）

各棟の平面図（1/600）には部屋の寸法が書かれている。部屋や廊下の位置は、まず**棟ごとの座標（ローカル座標）**で書き、全体座標に変換する。

| 項目 | 定義 |
|---|---|
| ローカル座標 (u, v) | 平面図を**図面のページどおりの向き**で見たとき、棟の外形の左上隅を原点、右が u、下が v（メートル） |
| 変換 | `全体座標 = 棟の基準点 + 回転(rotation) × (u, v)` |
| rotation | 0 / 90 / 180 / 270 のいずれか。配置図の棟はすべて縦横に沿って描かれているため、90度単位で足りる |

棟の基準点と rotation は、配置図の外形と平面図の外形を重ねて決める（手順書で作業を定める）。平面図と配置図で棟の向きが逆になっていることがあるため、階段や渡り廊下の位置を手がかりに、どちらが同じ端かを確かめる。

## 5. データ設計

### 5.1 データベースのテーブル（D1）

| テーブル | 内容 | 主な列 |
|---|---|---|
| `buildings` | 棟 | id, name, drawing_name, floors, outline（JSON文字列）, label_x, label_y, origin_x, origin_y, rotation |
| `nodes` | ノード | id, building_id, floor, kind, u, v, x, y, landmark |
| `edges` | 辺 | id, from_id, to_id, kind, oneway, closed |
| `rooms` | 部屋（目的地） | id, name, drawing_name, aliases（JSON文字列）, building_id, floor, node_id, category, description, visible |
| `checkpoints` | QRチェックポイント | id, node_id, facing, place |
| `config` | 設定 | key, value（`mapNorthBearing`・歩く速さ・`dataVersion` など） |
| `survey_notes` | 現地調査メモ | id, x, y, floor, building_id, kind, text, resolved, created_by, created_at |
| `change_log` | 変更履歴 | id, at, user_email, table_name, record_id, action, before（JSON）, after（JSON） |
| `admin_users` | 管理コンソールの利用者 | email, pass_hash, pass_salt, role, disabled, failed_count, locked_until, last_login_at |
| `admin_sessions` | ログイン中のセッション | token_hash, email, expires_at |

- すべてのデータ用テーブルに `updated_at`・`updated_by` を持たせる
- テーブル定義は `migrations/0001_init.sql` に書き、wrangler の機能で D1 に適用する
- 外形・別名のような配列は、JSON文字列として1つの列に入れる（テーブルを増やさず、高校生にも読みやすくするため）

### 5.2 型定義（`src/types.ts`）

画面・Functions・検査で共通に使う。データベースの列名（snake_case）は、API で返すときにこの型（camelCase）に変換する。

```ts
/** 全体座標の点（メートル） */
export type Point = { x: number; y: number };

/** 棟 */
export type Building = {
  id: string;            // 施設台帳の棟番号。例: "1", "28", "57"
  name: string;          // 来校者向けの名前。例: "管理・教室棟"
  drawingName: string;   // 図面上の名前。例: "管理，教室棟"
  floors: number;        // 階数
  outline: Point[];      // 外形（全体座標・時計回り）。全体マップの描画に使う
  label?: Point;         // 棟名を表示する位置（省略時は外形の中心）
  origin?: Point;        // ローカル座標の原点（全体座標）。平面図を入力した棟のみ
  rotation?: 0 | 90 | 180 | 270;
};

/** ノードの種類 */
export type NodeKind =
  | "corridor"   // 廊下の曲がり角・分岐
  | "door"       // 部屋の入口
  | "entrance"   // 棟の出入口
  | "stairs"     // 階段（各階に1つずつノードを置く）
  | "outdoor";   // 屋外の分岐・目印

/** ノード */
export type GraphNode = {
  id: string;           // 例: "B1-1F-C02"
  building?: string;    // 屋外なら省略
  floor: number;        // 屋外は 1
  kind: NodeKind;
  local?: { u: number; v: number }; // 棟のローカル座標（4.4）。平面図の寸法から入力
  pos?: Point;          // 全体座標。屋外ノード、または地図をタップして置いたノード
  landmark?: string;    // 目印の説明。例: "正面の階段" "自動販売機のある出入口"
};
// local と pos はどちらか一方を入力する。local を入力した場合、
// サーバーが棟の origin と rotation から pos を計算して返す。手で変換しなくてよい。
// 地図をタップして棟の中に置いた場合は、逆に pos から local を計算して保存する。

/** 辺 */
export type Edge = {
  from: string;
  to: string;
  kind?: "walk" | "stairs" | "bridge"; // 省略時は walk。bridge は2階の渡り廊下
  oneway?: boolean;     // 一方通行（基本は使わない）
  closed?: boolean;     // 一時的に通れない（工事など）
};

/** 部屋（目的地） */
export type Room = {
  id: string;           // 例: "R-28-1F-staff"
  name: string;         // 来校者向けの名前。例: "機械科 職員室"
  drawingName: string;  // 図面上の名前。例: "準備室"
  aliases?: string[];   // 検索用の別名。例: ["機械科", "機械"]
  building: string;
  floor: number;
  node: string;         // 入口のノードID（案内の終点）
  category: "admin" | "department" | "general" | "special";
  description?: string; // 到着時に出す一言
  visible: boolean;     // false なら来校者の一覧に出さない（準備中など）
};

/** QRチェックポイント */
export type Checkpoint = {
  id: string;           // URLに入る地点ID。例: "CP01"
  node: string;         // 対応するノードID
  facing: number;       // 掲示面の向き（図面角度）。壁から外に向かう方向
  place: string;        // 掲示場所の説明。例: "事務室窓口の右側の壁"
};

/** 来校者向けAPIが返す全データ */
export type CampusData = {
  version: number;      // データの版。保存のたびに1増える
  config: { mapNorthBearing: number | null; walkSpeed: number; stairSeconds: number };
  buildings: Building[];
  nodes: (GraphNode & { pos: Point })[]; // pos は必ず計算済み
  edges: Edge[];
  rooms: Room[];        // 経路のない部屋・visible=false の部屋は含めない（F-55）
  checkpoints: Checkpoint[];
};
```

| 対象 | 形式 | 例 |

### 5.5 データの検査（F-54・F-55）

検査は `src/core/validate.ts` に1つだけ書き、**サーバー（保存時）**と**管理コンソール（画面表示）**の両方で使う。

| 区分 | 検査 | 保存時の扱い |
|---|---|---|
| 致命的 | ID の重複 | **保存しない** |
| 致命的 | 存在しないノード・棟を指している（辺・部屋・チェックポイント） | **保存しない** |
| 致命的 | ノードに `local` と `pos` のどちらもない／`local` を使う棟に `origin`・`rotation` がない | **保存しない** |
| 致命的 | 階が棟の階数を超えている／`facing` が 0〜360 の外 | **保存しない** |
| 致命的 | 他から参照されているノードの削除（先に辺・部屋を消す必要がある） | **保存しない** |
| 注意 | 事務室（CP01）のノードから経路がない部屋 | 保存する。その部屋は来校者の一覧に出さない（F-55） |
| 注意 | 階段の辺の両端が、同じ棟で階が1つ違いになっていない | 保存する。一覧で示す |
| 注意 | 屋内ノードが棟の外形の外にある | 保存する。一覧で示す |
| 注意 | どの辺ともつながっていないノード | 保存する。一覧で示す |

### 5.6 API

すべて `functions/api/` に置く。

**来校者向け（認証なし・読み取りのみ）**

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/data` | `CampusData`（5.2）を返す。`version` を ETag にし、変わっていなければ 304 を返す（通信量を減らす） |

**ログイン**

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/api/auth/login` | メールアドレスとパスコードでログインし、セッションのクッキーを受け取る |
| POST | `/api/auth/logout` | ログアウト |

**管理コンソール向け（ログインが必要。`functions/api/admin/_middleware.ts` が確認する）**

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/admin/whoami` | ログイン中の利用者（メールアドレス・教員か生徒か） |
| GET | `/api/admin/data` | すべてのデータ（非表示の部屋・現地調査メモを含む）と検査結果 |
| POST / PUT / DELETE | `/api/admin/{buildings｜nodes｜edges｜rooms｜checkpoints｜survey}` | 1件の追加・修正・削除。保存前に検査し、致命的な誤りがあれば 400 とその理由を返す |
| GET | `/api/admin/history` | 変更履歴（新しい順） |
| POST | `/api/admin/history/{id}/undo` | その変更を元に戻す（戻した操作も履歴に残る） |

保存の処理の流れ（サーバー側）:

1. `_middleware.ts` がセッションのクッキーを確かめ、変更者のメールアドレスを得る。ログインしていなければ 401
2. 現在のデータに今回の変更を当てはめたものを `validate.ts` で検査する
3. 致命的な誤りがなければ、変更・`change_log` への記録・`dataVersion` の加算を**1つのまとまり（バッチ）**で D1 に書く
4. 新しい検査結果（注意の一覧）を返す

**同時編集**: 同じレコードを2人が同時に直した場合は、後から保存した方が残る。生徒の担当を棟ごとに分けて、ぶつからないようにする。

### 5.7 管理コンソールの認証（個人ごとのパスコード）

Cloudflare Access は無料プランでも支払い情報の登録が必要だったため、アプリ側でログインを作る（2026-10-28 決定）。

| 項目 | 内容 |
|---|---|
| ログインID | 学校のメールアドレス（大文字・小文字は区別しない） |
| パスコード | 教員が発行する12文字（`XXXX-XXXX-XXXX`）。読み間違えやすい 0/O・1/I/L を使わない。入力時のハイフン・小文字・空白は無視する |
| 保存のしかた | パスコードそのものは保存しない。PBKDF2-SHA256（10万回）でハッシュにし、利用者ごとのソルトと一緒に `admin_users` に保存する |
| セッション | ログインすると32バイトのランダムなトークンを発行し、クッキー（`HttpOnly`・`Secure`・`SameSite=Strict`）に入れる。データベースにはトークンの SHA-256 だけを `admin_sessions` に保存する。有効期間は7日 |
| 総当たり対策 | 5回続けて間違えると、そのアドレスは15分間ログインできない |
| 他サイトからの書き込み対策 | クッキーは `SameSite=Strict`。さらに管理用APIの書き込みは `Content-Type: application/json` だけを受け付ける |
| 権限 | `teacher`（教員）と `student`（生徒）。当面は同じ操作ができる。教員だけの操作（利用者の管理など）が必要になったら role で分ける |
| 利用者の管理 | 教師用PCで `tools/issue_passcodes.ts` を実行し、発行したパスコードを配る。メールアドレスの一覧（`local/admin-users.txt`）と配布用のパスコード（`local/passcodes.txt`）は**公開リポジトリに入れない** |
| 停止 | `admin_users.disabled = 1` にするとログインできなくなる（卒業・担当替え） |

## 6. 経路案内の計算

すべて `src/core/` の純粋な関数として作り、Vitest でテストする。

### 6.1 経路探索

- 辺の重み＝2点間の距離（座標から計算）。階段は「上下1階あたり10m」を加算し、なるべく階段を使わない経路を選ばせる
- `closed: true` の辺は除外する
- アルゴリズムは**ダイクストラ法**（ノードが数百個なので十分速い。高校の授業で扱える）

### 6.2 区間（ステップ）への分割

経路のノード列をそのまま案内すると「次へ」の回数が多すぎる。次の規則でまとめて**区間**にする。

区間の切れ目にするノード:

1. 曲がる角度が **30度以上** のノード
2. 棟の出入口（`entrance`）
3. 階段（階が変わる）
4. QRチェックポイントのノード
5. 目的地

切れ目でないノード（ほぼまっすぐ進む途中の点）は、前の区間に含める。

### 6.3 曲がる方向の判定（F-23）

区間の切れ目で、入ってくる向きと出ていく向きの差 Δ（−180〜180度）から決める。センサーは使わない。

| Δ | 表示 |
|---|---|
| −30〜30度 | まっすぐ |
| 30〜150度 | 右へ |
| −150〜−30度 | 左へ |
| 150度以上 | 引き返す |
| 階が変わる | 階段で○階へ（上る/下りる） |

### 6.4 案内文の組み立て

```
{目印}まで 約{距離}m 進み、{曲がる方向}
例: 「ホール横の階段まで 約18m 進み、階段で2階へ」
```

- 目印はノードの `landmark`。未入力なら「突き当たり」「次の角」などの既定の言葉を使う
- 距離は5m単位で丸める（細かい数字は来校者にとって意味がない）
- 所要時間は、歩く速さ 1.0 m/s ＋ 階段1階あたり15秒で見積もる（`config` テーブルで変更可）

### 6.5 現在地の扱い

```ts
type NavState = {
  route: Step[];          // 区間の列
  stepIndex: number;      // 今いる区間
  anchor?: {              // 最後にQRで確定した情報
    checkpointId: string;
    headingOffset: number; // 6.6 で使う
    at: number;            // 時刻（ms）
    stepsSince: number;    // その後に「次へ」を押した回数
  };
};
```

- 「次へ」で `stepIndex + 1`、「戻る」で `−1`
- QRを読んだとき（F-30〜F-32）:
  - 経路上のチェックポイント → `stepIndex` をその区間に合わせる
  - 経路外 → そのノードから経路を引き直す

### 6.6 向きの推定（AR表示用）

利用者が今どちらを向いているかを、図面角度で求める。

```
利用者の向き（図面角度） = 端末の回転角 + headingOffset
```

| 場面 | 処理 |
|---|---|
| QRを読んだ瞬間 | 利用者はQRの正面に立ち、カメラを壁に向けている。つまり利用者の向き＝`facing + 180`。このときの端末の回転角との差を `headingOffset` として保存する |
| その後 | ジャイロによる端末の回転角に `headingOffset` を足すだけ。磁気は使わない |
| QRを一度も読んでいない | 出発点のQRから開いた場合は、その時点で確定済み。URL直接の場合は「向き不明」 |
| 補助（`mapNorthBearing` 設定後） | 屋外で、向き不明または信頼度が低いときに限り、コンパスの方位から `headingOffset` を作る |

端末の回転角:

- **iPhone**: `deviceorientation` の `alpha`（起動時を基準とした相対角）。`webkitCompassHeading` は磁気なので補助のときだけ使う
- **Android**: `deviceorientation`（相対）。補助のときは `deviceorientationabsolute`
- スマホを**縦に立ててカメラを前に向けた持ち方**でも正しく出るよう、`alpha / beta / gamma` から**カメラの向いている方向を水平面に投影した角度**を計算する（`src/core/heading.ts`）

**信頼度**（F-42）:

| 状態 | 信頼度 | 矢印の表示 |
|---|---|---|
| QRを読んでから2分以内かつ「次へ」3回以内 | 高 | 通常 |
| それ以外でオフセットあり | 低 | 半透明＋「QRを読むと正確になります」 |
| 向き不明・センサー許可なし | なし | 矢印を出さず、文字の案内のみ |

## 8. カメラ表示（AR）の描画

### 8.1 矢印の重ね表示（F-41）

1. `getUserMedia({ video: { facingMode: "environment" } })` で背面カメラを `<video>` に表示
2. 次に向かう方向 `target`（図面角度・6章）と、利用者の向き `heading`（6.6）の差 `rel = target − heading` を求める
3. 矢印（SVG）を `rel` だけ回転させ、CSS の `perspective` と `rotateX` で**地面に寝かせたように**見せる
4. 端末の回転に合わせて毎フレーム（`requestAnimationFrame`）更新する。値のぶれは移動平均でならす

床に正確に貼り付けるわけではない（平面検出をしない）。「前方の地面に矢印がある」ように見える表現にとどめる。

### 8.2 QRを基準にした矢印（マーカーAR・F-43）

QRの位置と向きが分かっている瞬間だけ、矢印を実際の壁に合わせて表示する。

1. jsQR でQRを読むと、映像上の**QRの四隅の座標**が得られる
2. 正方形（QR）→ 映像上の四角形 への**射影変換（ホモグラフィ）**を計算する（4点から8つの係数を解く）
3. その変換を CSS の `matrix3d` にして、矢印の要素に適用する → 矢印がQRの貼られた壁の上に描かれる
4. 矢印の向きは、次に進む方向と壁の向きの関係から決める（壁に沿って右・左、または背後）

three.js などの3Dライブラリは使わない（CSSだけで実現でき、生徒が中身を理解しやすい）。

### 8.3 カメラが使えないとき（F-28 相当）

- 許可されない・カメラがない → カメラボタンを無効にし、③の画面だけで案内する
- HTTPS でないとカメラが使えないため、ローカルで実機テストするときの方法を手順書に書く

**バックアップ**: D1 は30日前までの任意の時点に戻せる（Time Travel 機能）。加えて、教員が定期的に `wrangler d1 export` でSQLファイルに書き出して保管する。
