## 1. 目的

延岡工業高校は校舎・実習棟が約25棟あり、室数も約150室と多い。初めて来校した人は、事務室で目的の部屋を聞いても、たどり着くのが難しい。

本アプリは次の2段階で来校者を案内し、迷いを減らす。

1. **まず全体像を見せる**: 学校全体の地図に「現在地」と「目的地」を表示し、これからどこへ向かうのかを把握してもらう
2. **次に一歩ずつ案内する**: 目印ごとに区切った道順を、地図・文字・矢印（カメラ映像に重ねた矢印を含む）で示す

## 2. 利用者と利用シーン

### 2.1 主な利用者

| 利用者 | 特徴 |
|---|---|
| **来校者（主対象）** | 保護者・業者・オープンスクール参加者・他校の教員など。校内の地理を知らない。アプリのインストールはしない |
| 生徒・教職員（副次） | 来校者の案内役。アプリの動作確認・データ整備も担う |

### 2.2 代表的な利用シーン

1. 来校者が、正門から案内板に従って**事務室の窓口**に来る
2. 窓口に置いたQRコードをスマートフォンで読む → ブラウザでアプリが開く（インストール不要）
3. 目的地（例: 職員室、機械科職員室）を一覧から選ぶ
4. **学校全体の地図が表示され、現在地（事務室）と目的地にピンが立ち、その間の道順が線で示される**。所要時間や階数も表示される。来校者は「今からここへ行く」と全体像をつかんでから「案内開始」を押す
5. 案内が始まると「次の目印」と進む方向が表示される。目印に着いたら「次へ」をタップする。棟の入口や階段にQRがあれば、読むことで現在地と向きを確かめ直せる（読まなくてもよい）
6. 必要なら、カメラ表示（AR）に切り替えて、実際の景色に重ねた矢印で方向を確かめる
7. 目的の部屋の前で「到着」と表示される

## 3. 用語

| 用語 | 意味 |
|---|---|
| 図面座標 | 施設台帳の図面から起こした、校地全体共通の平面座標（単位メートル） |
| ノード | 経路上の地点（曲がり角・入口・階段・部屋の前など）。図面座標と階を持つ |
| チェックポイント | QRコードを掲示するノード。読むと現在地と向きが確定する |
| 掲示面の向き | QRを貼った壁がどちらを向いているか。図面から決まる。QRを正面から読んだ人の向き＝この向きの反対 |
| 区間 | 隣り合う目印の間の移動。「次へ」1回で進む単位 |
| 全体マップ | 配置図（図面1ページ目）をもとに描いた学校全体の地図 |
| 階マップ | 1つの棟の、ある階の平面図をもとに描いた地図 |

## 4. 前提と制約

| 区分 | 内容 |
|---|---|
| 端末 | 来校者自身のスマートフォン。**iPhone（Safari）と Android（Chrome）の両方**に対応する |
| 配布形態 | Webアプリ。インストール不要。QRコードからURLを開く |
| 通信 | 来校者のモバイル回線を利用する（校内Wi-Fiは前提にしない） |
| 公開先 | **Cloudflare Pages**（HTTPS。カメラとセンサーの利用に必要）。データは **Cloudflare D1**（SQLite互換のデータベース）に保存する。管理コンソールで入力したデータを保存するため、当初予定していた「DBが必要になったら Cloudflare へ移行」を前倒しした |
| 技術 | **React ＋ Vite**（TypeScript）。サーバー側の処理は Cloudflare Pages Functions。GitHub に push すると Cloudflare 上でビルドされる |
| 開発環境 | プログラムは**教師用PC**（Node.js v24・git 導入済み）で教員（＋Claude）が書く。コマンドの実行方法は、手順書とその都度の案内で示す |
| 生徒の端末と担当 | 生徒の端末は **Chromebook とスマートフォン**（Node.js・git は使えない）。生徒の担当は**管理コンソールでのデータ入力・現地調査・テスト**とし、プログラムは書かない |
| 管理者の認証 | 管理コンソールには、教員が発行した**個人ごとのパスコード**（学校のメールアドレス＋パスコード）でログインした人だけが入れる。Cloudflare Access は無料プランでも支払い情報の登録が必要だったため採用しない（2026-10-28） |
| データの正 | **施設台帳の図面（令和7年度）を唯一の正とする**。現地確認で図面と食い違った点は、データ側に記録して上書きする |
| 方位の扱い | **進む方向は図面座標から計算する**。利用者の向きはQRを読んだ時点で確定させ、その後の回転はジャイロで追う。**磁気コンパスは精度を上げるための補助に限る**。必要になった時点で方位を現地で実測する |
| AR表現 | 床に貼り付く本格的なAR（WebXR・平面検出）は使わない。カメラ映像に矢印を重ねる表示と、QRを基準にした矢印表示（可能なら）に限る（10章） |
| 期限 | **2026-12 下旬（約2か月）までにMVPを動かす** |

## 5. 機能要件

優先度: **M** = MVPに必須 / **S** = MVP後に追加（余裕があればMVPに入れる） / **C** = 余力があれば

### 5.1 起動と現在地の決定

| ID | 要件 | 優先度 |
|---|---|---|
| F-01 | 事務室窓口のQRを読むと、アプリが開き、**現在地＝事務室前・向き＝確定済み**の状態で始まる | M |
| F-02 | **事務室以外のチェックポイントのQRを読んで開いた場合は、そのQRの地点を現在地として始まる**（QRごとに地点IDをURLに含める） | M |
| F-03 | QRを使わずにURLを直接開いた場合は、現在地を事務室前として始める。画面上で現在地を変更できることを示す | M |
| F-04 | 現在地を、全体マップ上のチェックポイントか一覧から**手動で選び直せる** | S |
| F-05 | 初回の案内開始時に、カメラと動きセンサーの利用許可を求める（iPhoneはボタン操作が必須）。許可しなくても案内は使える | M |

### 5.2 目的地の選択

| ID | 要件 | 優先度 |
|---|---|---|
| F-10 | 目的地を**カテゴリ別の一覧**（管理棟／各科の職員室など）から選べる | M |
| F-11 | 一覧には**来校者向けの名前**（例:「機械科 職員室」）を表示する。図面上の名前（例: 28棟1階「準備室」）とは別に管理する | M |
| F-12 | 部屋名の一部を入力して検索できる（例:「保健」→ 保健室） | S |
| F-13 | 部屋の別名で検索できる（例:「情報」→ 情報技術科 職員室） | S |

### 5.3 全体マップ（行動の全体像の提示）

| ID | 要件 | 優先度 |
|---|---|---|
| F-15 | 目的地を選ぶと、**学校全体の地図（配置図1ページ目に相当）を表示**する。各棟の形と棟名が描かれている | M |
| F-16 | 全体マップに**現在地（出発点）と目的地のピン**を立て、その間の**道順を線で描く** | M |
| F-17 | 全体マップの下に、目的地の棟名・階・**おおよその距離と所要時間**・通る主な目印（例:「渡り廊下を通って2階へ」）を表示する | M |
| F-18 | 全体マップは指で拡大・移動できる。目的地が別の階なら「2階」と分かるように表示する | M |
| F-19 | 「案内開始」で一歩ずつの案内（5.4）に進む。案内中も、いつでも全体マップに戻って現在の位置を確認できる | M |
| F-20 | 目的地のある棟の**階マップ**を表示し、部屋の位置を示す | S |

### 5.4 一歩ずつの案内（中核機能）

| ID | 要件 | 優先度 |
|---|---|---|
| F-21 | 現在地から目的地までの経路を、図面から作った経路データで計算する | M |
| F-22 | 画面に「**次の目印**」を文字で出す（例:「正面の階段まで約12m」「右手の出入口から外へ」） | M |
| F-23 | 曲がる方向（右・左・直進・階段を上る）を、**経路の形から計算して示す**。センサーが使えなくても案内できる | M |
| F-24 | 目印に着いたら、利用者が「**次へ**」をタップして次の区間に進む。**QRを読まなくても進める** | M |
| F-25 | 「**戻る**」で直前の区間に戻れる（押し間違い対策） | M |
| F-26 | **階の移動**を案内する（「この階段で2階へ」）。2階の渡り廊下を通る経路も扱う | M |
| F-27 | 案内中は、全体マップを縮小した表示に、今いる区間を強調して示す | M |
| F-28 | 目的地に着いたら「到着」を表示する | M |

### 5.5 QRチェックポイント（任意の補正）

| ID | 要件 | 優先度 |
|---|---|---|
| F-30 | 案内中に、アプリ内で**いつでも**QRを読める。読むと現在地と向きが確定し、ずれていた分を補正する | M |
| F-31 | QRを読むことは**必須ではない**。案内画面では、目印にQRがあることを知らせるだけにとどめる | M |
| F-32 | 経路から外れた場所のQRを読んだ場合は、その地点から経路を引き直す | M |
| F-33 | QRは**棟の出入口・階段・渡り廊下の端**など、迷いやすい要所に限定して掲示する | M |
| F-34 | QRは、スマートフォン標準のカメラで読んでもアプリが開く（F-02と同じ仕組み） | M |

### 5.6 カメラ表示（AR）

| ID | 要件 | 優先度 |
|---|---|---|
| F-40 | 案内画面は**マップと文字の表示を基本**とし、ボタンで**カメラ表示（AR）**に切り替えられる | M |
| F-41 | カメラ表示では、カメラ映像の上に、次に進む方向を示す矢印を重ねる。スマートフォンを回すと矢印も回る | M |
| F-42 | 向きの信頼度が低いとき（QRを長く読んでいない、センサーの許可がないなど）は、矢印を薄く表示し「QRを読むと矢印が正確になります」と知らせる | M |
| F-43 | **QRを読んだ瞬間、カメラ映像のQRの位置を基準に、進む方向を示す矢印を立体的に重ねる**（マーカーAR）。図面上で向きが分かっている壁を基準にするので、最も正確に方向を示せる | S |
| F-44 | 到着時、カメラ映像に目的の部屋の名前と方向を表示する | C |

### 5.7 管理コンソール（生徒・教員向け）

Chromebook とスマートフォンのブラウザで使う、データ入力用の画面。来校者向けの画面とは別のURL（`/admin`）にする。

| ID | 要件 | 優先度 |
|---|---|---|
| F-50 | 教員が発行したパスコードでログインした人だけが使える。来校者は入れない。ログインは7日間続く | M |
| F-51 | 棟・ノード・辺・部屋・チェックポイントのデータを、画面から**追加・修正・削除**できる。保存すると**すぐに来校者向けの画面に反映**される | M |
| F-52 | 全体マップ・階ごとの地図の上で、**タップしてノードを置く／2つのノードをタップして辺でつなぐ**操作ができる（Chromebook での操作を主とする） | M |
| F-53 | 屋内のノードは、平面図の寸法から求めた**棟の中の座標（数値）**でも入力できる | M |
| F-54 | 保存時にデータを自動で検査する。**致命的な誤り**（存在しないノードを指す、IDの重複など）は保存しない。**注意**（事務室から経路がない部屋など）は画面に一覧で示す | M |
| F-55 | 経路がつながっていない部屋は、来校者向けの目的地一覧に**表示しない**（入力途中のデータが来校者に見えないようにする） | M |
| F-56 | 出発点と目的地を選んで、**経路と案内文を管理コンソール上で確認**できる | M |
| F-57 | 誰が・いつ・何を変更したかの**変更履歴**を残し、1件ずつ**元に戻せる** | M |
| F-58 | **現地調査メモ**: スマートフォンで地図上の位置をタップし、出入口・通れない場所・目印などのメモを残せる。後で Chromebook からそのメモを見ながらノードを置ける | M |
| F-59 | 部屋の寸法を上から順に入力すると、扉の前のノードを自動で並べる**寸法入力の補助** | S |
| F-66 | 平面図の画像を地図の下に敷いて表示する（画像は認証した人にだけ配信し、一般には公開しない） | S |
| F-67 | 棟の外形の修正 | S |
| F-68 | QRコードの印刷用シート（地点名・掲示面の向き・掲示場所の説明つき）を出力できる。**作成は教員の依頼時** | S |
| F-69 | 現地調査メモへの写真の添付 | C |

## 6. 非機能要件

| 区分 | 要件 |
|---|---|
| 対応環境 | iOS 16以降の Safari、Android 10以降の Chrome。縦持ちのみ |
| 表示速度 | モバイル回線でQRを読んでから3秒以内に最初の画面が出る |
| 矢印の精度 | QRで向きを確定した直後は、進む方向と矢印のずれが **±20度以内**。ジャイロのずれはQRを読むたびに解消する |
| 操作性 | 初めての来校者が**説明なしで**目的地を選び、全体マップを見て、案内を開始できる。文字は大きく、操作ボタンは親指で届く位置に置く |
| 安全 | 歩きながら画面を見続けないよう、注意文を表示する。カメラ表示は「立ち止まって方向を確かめる」使い方を基本とし、階段の手前では立ち止まるよう促す |
| プライバシー | カメラ映像・位置情報は端末の外に送らない。利用者の個人情報は扱わない |
| 情報の公開範囲 | 公開するのは案内に必要な棟の形・部屋名・経路のみ。**施設台帳PDF・図面画像はリポジトリに含めない**（地図はデータから描く）。管理コンソール用の図面画像（F-66）は認証した人にだけ配信する |
| 管理コンソールの安全 | パスコードは推測されにくい12文字を教員が発行し、データベースにはハッシュ（元に戻せない形）だけを保存する。5回続けて間違えると15分間ログインできなくする。すべての管理用APIの前でログインを確認する。変更履歴に変更者のメールアドレスを残す |
| 保守性 | データ（データベース）とプログラムを分け、部屋の追加にプログラムの変更が要らないようにする。生徒は管理コンソールだけでデータを整備できる |
| 費用 | 運用費は0円（Cloudflare の無料枠: Pages・Pages Functions・D1）。**支払い情報は登録しない**ので、無料枠を超えても課金されない |
| 管理コンソールの対応環境 | Chromebook の Chrome（主）、スマートフォン（現地調査メモ・確認） |

## 7. データ要件

すべてのデータは Cloudflare D1 に保存し、管理コンソールから編集する。

| データ | 内容 | 出典 |
|---|---|---|
| 棟 | 棟番号・名称・**外形（全体マップの描画用）**・階数・図面上の位置と回転 | 配置図（1/1600） |
| 部屋 | **来校者向けの名前**・図面上の名前・別名・棟・階・入口ノード・カテゴリ | 平面図（1/600）＋教員への確認 |
| ノード | ID・図面座標(x, y)・階・種類（廊下/入口/階段/部屋前/屋外）・目印の説明文 | 平面図＋配置図＋現地確認 |
| 辺（つながり） | ノードとノードの接続・通行可否 | 現地確認 |
| チェックポイント | QRの地点ID・ノード・**掲示面の向き**（図面座標での角度） | 図面＋現地での掲示 |
| 現地調査メモ | 位置・種類・メモ・記録者 | 現地調査（スマートフォン） |
| 変更履歴 | 日時・変更者・対象・変更前後の値 | 自動で記録 |

- 距離と方向は**データに持たず、座標から計算する**（二重管理による食い違いを防ぐ）
- 全体マップは、棟の外形データから描く（図面画像を使わない）
- 方位を実測した場合は「図面の上方向が北から何度か」という**1つの値だけ**を持つ

## 10. 方式の要点

### 10.1 現在地と進み方

1. 出発点は、開いたQRの地点（基本は事務室）
2. 「次へ」で区間を1つずつ進む。アプリは「利用者は今この区間にいる」と扱う
3. 要所のQRは**任意**。読めば現在地と向きが確定し、読まなければ「次へ」の操作どおりに進んだものとして扱う

### 10.2 案内の伝え方（3つの層）

| 層 | 内容 | センサー | 位置づけ |
|---|---|---|---|
| ① 全体マップ | 出発点・目的地・道順の線 | 不要 | 案内開始前に全体像を見せる |
| ② 文字と曲がる方向 | 「突き当たりを右」「階段で2階へ」 | 不要（経路の形から計算） | **案内の主役**。どの端末でも必ず動く |
| ③ カメラ表示（AR） | 景色に重ねた矢印 | ジャイロ（＋補助のコンパス） | 分かれ道や屋外の広い場所で、方向を実際の景色で確かめるための補助 |

### 10.3 AR機能をどこで使うか

カメラに矢印を重ねる表示は「矢印がどの方向を向くべきか」をスマートフォンが知っていないと成立しない。屋内ではGPSが使えないため、向きの手がかりは次の3つに限られる。

| 手がかり | 精度 | 使いどころ |
|---|---|---|
| QRを読んだ瞬間（掲示面の向きが図面から分かる） | 高い | **QRの地点でのマーカーAR（F-43）**。ARが最も有効に働く場面 |
| ジャイロ（最後にQRを読んでからの回転） | 時間とともにずれる | QRから数区間の間のカメラ表示 |
| 磁気コンパス | 鉄骨の校舎内では乱れる。屋外では比較的使える | 屋外の区間での補助 |

このため、ARが有効に働くのは主に次の場面と判断する。

- **QRを読んだ地点**: QRの位置を基準に、「ここからこっちへ」を立体的に示せる
- **屋外の広い場所**（実習棟エリアなど）: 目印になる壁や廊下がなく、文字だけでは方向が伝わりにくい。コンパスも比較的安定している

逆に、廊下の一本道ではARの効果は小さい。そのため、ARは常時表示ではなく、**利用者が切り替えて使う補助機能**とする。

## 11. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| 図面に出入口・屋外通路が書かれていない | 各科職員室までの経路が作れない | **最初の2週間で現地調査**を行う（手順書に調査シートを用意） |
| 全体マップ用に全棟の外形を読み取る作業量 | データ作成が遅れる | 外形は長方形で近似し、MVPの経路に関係する棟から順に精度を上げる |
| 配置図の読み取り誤差（±1m程度） | 全体マップと矢印の向きが数度ずれる | 区間の長さに対して許容範囲。QRで補正できる |
| QRを読まない利用者が多い | 向きが分からず、AR表示の矢印がずれる | 案内の主役は文字と曲がる方向（センサー不要）。ARは信頼度を表示する（F-42） |
| ジャイロのずれ（数分で数度〜十数度） | QRから遠い区間でAR表示の矢印がずれる | 同上 |
| iPhoneのセンサー許可 | 許可しないと矢印が回らない | 許可しなくてもマップと文字で案内できる |
| 2か月で全6学科まで終わらない | MVPが間に合わない | **管理棟の5室を最優先**で完成させ、各科職員室は1棟ずつ追加する |
| 管理コンソールの開発で作業量が増える | 来校者向けの画面が遅れる | 管理コンソールは F-50〜F-58 に絞る。データ入力を早く始められるよう、管理コンソールを**来校者向けの画面より先に**作る |
| 保存が即反映される | 入力途中・誤ったデータが来校者に見える | 致命的な誤りは保存させない（F-54）。経路のない部屋は一覧に出さない（F-55）。変更履歴から戻せる（F-57） |
| 管理コンソールの利用者の管理 | 卒業・担当替えの後も編集できてしまう／パスコードの漏えい | 利用者の登録・停止・パスコードの再発行は教員が教師用PCで行う。年度末に見直す |
| 「次へ」の押し忘れ・押しすぎ | アプリ上の現在地と実際がずれる | 「戻る」ボタン、全体マップでの現在位置の確認、QRでの補正 |
| 施設情報の公開 | 校内の配置が外部に知られる | 公開範囲を棟の形・部屋名・経路に限定し、図面は非公開。公開前に管理職の了承を得る |
